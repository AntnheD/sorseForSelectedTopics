# Task definition and evaluation protocol

## 1. Task statement

**Intended user.** A developer who is building or maintaining a FastAPI service and wants a
quick, trustworthy answer from the official FastAPI documentation without reading the whole
page tree.

**Input.** One natural-language question about FastAPI usage, in English, typed as a single
string (for example "How do I make a query parameter optional?").

**Output.** One of:

1. A concise answer (one to three sentences) plus **citations**: the documentation file and
   section (`tutorial/query-params.md § Optional parameters`) of every retrieved passage that
   supports a sentence of the answer.
2. An explicit **insufficient-evidence response** ("I could not find enough evidence in the
   FastAPI documentation to answer this question") together with the reason (weak retrieval,
   the model reported it does not know, or too few answer sentences are supported by the
   passages) and the closest passages so the user can judge for themselves.

**What counts as correct, complete and supported.**

| Criterion | Definition used in this project |
|---|---|
| Correct | Every factual claim in the answer agrees with the cited documentation at the corpus commit. A wrong parameter name, default value or version is incorrect. |
| Complete | All `expected_answer_points` of the question are present (e.g. for "dev vs run" both the reload behaviour and the listening address). Missing a point makes the answer partially complete (scored 0.5 in manual review). |
| Supported | Each sentence can be traced to a retrieved passage: at least `min_sentence_support` (0.35) of its content words appear in that passage. Sentences below this threshold are flagged as unsupported and never receive a citation. |
| Valid citation | A citation genuinely supports a claim only if the cited passage states that claim (checked by a person in the manual review CSV). A citation that points at the right file but a section that does not contain the claim is counted as invalid. |
| Correct abstention | For questions whose topic is absent from the corpus the system must abstain; for answerable questions it must not. |

**Out of scope.** General Python help, questions about other frameworks, questions whose
answer is not in the documentation subset below. The system is not a general programming
assistant.

## 2. Corpus provenance

* Source: the English documentation of https://github.com/fastapi/fastapi, directory
  `docs/en/docs`, plus the example code in `docs_src` that the pages include.
* Commit: `5cb6272ed7e3e07eaf6978e1e65b94aca76fa8e0`, committed 2026-11-02.
  Fetched on 2026-11-03 with `bash scripts/fetch_docs.sh` (sparse git clone, pinned commit).
  The commit hash is also written into every chunk as `doc_version`.
* License: MIT (FastAPI repository). The copied files are kept unchanged under
  `data/documents/fastapi/`; `data/documents/fastapi/SOURCE.md` is generated by the script.
* Included (115 Markdown files, ~97k words): `tutorial/` (51), `advanced/` (35),
  `deployment/` (9), `how-to/` (12) and the core pages `index.md`, `features.md`, `async.md`,
  `python-types.md`, `environment-variables.md`, `virtual-environments.md`, `fastapi-cli.md`.
* Excluded, with reasons: `reference/` (mkdocstrings stubs, no prose), `release-notes.md`
  (changelog noise), community/meta pages (`about/`, `learn/`, `resources/`, sponsors, people,
  newsletter, translations, contributing, benchmarks, alternatives, history, project
  generation, editor support), images/CSS/JS. `_llm-test.md` is copied but excluded at
  preprocessing time through `corpus.exclude_files` because it is a synthetic translation test.
* Version-specific behaviour: the docs describe FastAPI at that commit (for example the
  401-vs-403 change in 0.122.0, the deprecation of `fastapi.middleware.wsgi`). Answers are
  only claimed to hold for that version; the system never states a version that the passages
  do not state.
* Known limitations: 10 chunks are exact duplicates because `index.md` repeats sections of
  `tutorial/first-steps.md` and `deployment/cloud.md`; one include (`fastapi/openapi/docs.py`)
  points at library source outside `docs_src` and is left as a marker.

## 3. Question-set schema

File: `data/evaluation/questions.json` (version 1.0, 58 questions). Each item has:

| Field | Meaning |
|---|---|
| `id` | stable id, `dev-01`, `val-07`, `test-12`, `test-ie-03` |
| `question` | user-style question |
| `category` | `direct`, `multi-step`, `comparison`, `troubleshooting`, `insufficient-evidence` |
| `split` | `dev`, `val` or `test` |
| `answerability` | `answerable` or `insufficient_evidence` |
| `expected_answer_points` | the facts a correct answer must contain (used in manual review) |
| `answer_keywords` | one group of alternatives per fact; used by the automatic keyword-coverage proxy |
| `relevant_sources` | `file#section-anchor` labels; checked to exist in the corpus by `python -m docqa check-questions` |
| `notes` | where in the docs the label was verified |

Labels were written by reading the cited section of the fetched docs. Insufficient-evidence
questions were chosen only after `grep` confirmed the topic (rate limiting, Sentry, request
body size limit, HTTP/3, Prometheus, gRPC, memcached) is absent from the corpus.

Split sizes: dev 8 answerable; val 12 answerable + 2 insufficient; test 31 answerable + 5
insufficient. This is a small benchmark: a single question changes a test-split rate by about
3 points, so differences smaller than that are not meaningful and are reported as such.

## 4. Split and leakage rules

* `dev` is used while developing code (debugging, sanity checks).
* `val` is the only split used to compare retrievers, chunk settings, top-k, source filters and
  abstention thresholds (`scripts/run_experiments.py`, `python -m docqa eval-answers --split val`).
* `test` is evaluated once, after the configuration is frozen in `configs/final.json` and the
  Git state is recorded in `reports/results.md`. If the system is changed after seeing test
  results, that is disclosed in `reports/results.md`.
* `validate_against_corpus` flags near-duplicate questions across splits (Jaccard ≥ 0.8 on
  question words); the current set has none.
* Questions sharing a topic across splits (for example optional vs required query parameters
  in dev and test) are deliberately different questions with different answers; they test
  whether retrieval distinguishes neighbouring sections.

## 5. Metrics (see `src/docqa/metrics.py`)

* **Relevance** of a retrieved chunk: at *source* level its file matches a label; at *section*
  level its `file#anchor` matches a label with an anchor (a label without anchor matches any
  section of that file).
* **Recall@k** = labelled sources found in the top k / labelled sources, per question, averaged.
* **HitRate@k** = 1 if any relevant chunk is in the top k; **Top-1** = HitRate@1.
* **MRR@k** = 1 / rank of the first relevant chunk if that rank ≤ k, else 0.
* Denominator: answerable questions in the split; insufficient-evidence questions are excluded
  from retrieval metrics and evaluated by abstention accuracy instead.
* Answer quality is evaluated separately (`src/docqa/evaluate_answers.py`): automatic proxies
  (keyword coverage, citation precision, support rate, abstention accuracy) and a manual
  rubric filled in for every test question.
